Brief for Claude Code

You are running on the user's Ubuntu/Debian build server. Use this guide to set up the device-tree toolchain and generate device, vendor and (optionally) TWRP trees for a RisingOS Revived 9.0 build.

Fill these in before starting (ask if any are unknown):

PlaceholderMeaningValue
<codename>Device codename (adb shell getprop ro.product.device)—
<vendor>Manufacturer folder name, lowercase (e.g. xiaomi, google)—
<firmware-file>Full stock firmware archive in ~/android-dt/firmware/—
<fingerprint>adb shell getprop ro.build.fingerprint—

Operating rules:

  • Work through Steps 1–8 in order. Mark each step done only after its verification command succeeds; report the output.
  • Do not rely on ~/.bashrc aliases in non-interactive shells: use source ~/android-dt/.venv/bin/activate instead of dtenv.
  • Never run sudo package installs, repo sync of a full ROM (hundreds of GB), or anything that deletes existing folders without confirming with the user first.
  • Never flash, fastboot or otherwise write to a phone. Step 8 Part 3 is for the user to do by hand.
  • Do not push device or vendor trees to any remote, and never to a public repo (vendor blobs are proprietary).
  • Commit to local git after each meaningful change, as the guide describes.
  • Release codes (cp2a) and branch names (seventeen) change; check the RisingOS Revived manifest README and vendor/lineage/vars/aosp_target_release before using them.

Overview

The toolchain turns a phone's stock firmware into a starting-point device tree in three moves: dump the firmware with dumpyara, generate a LineageOS/AOSP tree with aospdtgen (or a recovery tree with twrpdtgen), then hand-tune and test-build. The generators get you roughly 70–80% of the way; the rest is manual cleanup and boot testing.

An Android "device tree" is not one repo but a set of them that the ROM build system reads:

RepoPath in the ROM sourceWhat it holds
Device treedevice/<vendor>/<codename>BoardConfig.mk, device.mk, AndroidProducts.mk, lineage_<codename>.mk, partition sizes, overlays, init .rc files, fstab, sepolicy
Vendor treevendor/<vendor>/<codename>Proprietary blobs (HALs, firmware, libraries) pulled from the stock ROM by extract-files
Kernelkernel/<vendor>/<soc> or a prebuilt in the device treeKernel source, or a prebuilt Image/dtb/dtbo copied from stock
Recovery treedevice/<vendor>/<codename> in a TWRP sourceA separate, smaller tree for building TWRP only

aospdtgen only works on Treble devices (Android 8.0+ with VNDK). Check with adb shell getprop ro.treble.enabled; it should print true.

text
                         Stock firmware
                  (full OTA or fastboot ROM)
                 /                          \
        dumpyara (Step 3)            recovery.img or boot.img
               |                     (from the ROM, or dumpyara -d)
        Firmware dump  ------+                  |
               |             |           twrpdtgen (Step 5)
        aospdtgen (Step 4)   |                  |
               |             |           TWRP tree (omni_ names)
        Device tree          |                  |
               |             |         * Rename omni_ -> twrp_ (Step 5)
   extract-files.py (Step 6) <-- reads the dump |
               |                         TWRP build (Step 8)
        Vendor tree                      mka recoveryimage
               |
      * Clean up by hand (Step 7)
               |
      RisingOS build (Step 8)
      riseup, rise b

  * = hand-edited step; everything else is generated by a tool

The ROM path runs through the dump twice: once for aospdtgen, once for extract-files.py. The TWRP path needs only one image, plus a manual rename.

Prerequisites

You need a 64-bit Ubuntu/Debian host, your phone's exact codename, and its full stock firmware package. Tree generation itself is light; the test-build in Step 8 is what needs the big machine.

Keep all of this in one workspace, for example ~/android-dt/ with firmware/, dumps/ and trees/ folders, so nothing ends up scattered across your home directory.

Step 1Install base host packages

One apt command covers the extraction tools the Python generators shell out to (7-Zip, EROFS, LZ4, cpio), plus Python and git.

  1. Update and install the base packages:
shell
sudo apt update && sudo apt full-upgrade -y
sudo apt install -y \
  git git-lfs curl wget unzip zip \
  python3 python3-pip python3-venv python3-dev \
  p7zip-full erofs-utils lz4 brotli cpio \
  android-sdk-libsparse-utils xxd file
  1. Confirm Python is 3.9 or newer:
shell
python3 --version
  1. Install the latest adb/fastboot from Google's platform-tools (the distro packages are often stale):
shell
mkdir -p ~/bin && cd ~/bin
curl -LO https://dl.google.com/android/repository/platform-tools-latest-linux.zip
unzip -o platform-tools-latest-linux.zip
echo 'export PATH="$HOME/bin/platform-tools:$HOME/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
adb --version
  1. Set your git identity once, since you will commit the trees:
shell
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git lfs install
  1. Create the workspace:
shell
mkdir -p ~/android-dt/{firmware,dumps,trees}

If erofs-utils is missing on an older release, dumpyara cannot unpack EROFS partitions, which most Android 13+ phones use. Upgrade the distro or build erofs-utils from source before continuing.

Step 2Install dumpyara, aospdtgen and twrpdtgen

Install all three generators from PyPI into one virtual environment. Ubuntu 23.04+ and Debian 12+ block system-wide pip install (PEP 668), and a venv keeps the tools from fighting your system Python anyway.

  1. Create and activate the venv:
shell
python3 -m venv ~/android-dt/.venv
source ~/android-dt/.venv/bin/activate
python -m pip install --upgrade pip wheel
  1. Install the tools:
shell
pip install dumpyara aospdtgen twrpdtgen
  1. Verify each one runs:
shell
python -m dumpyara --help
python -m aospdtgen --help
python -m twrpdtgen --help
  1. Optional: add an alias so the venv is one word away in new shells:
shell
echo "alias dtenv='source ~/android-dt/.venv/bin/activate'" >> ~/.bashrc

To pick up upstream fixes later, run pip install --upgrade dumpyara aospdtgen twrpdtgen inside the venv. If PyPI lags behind a fix you need, install straight from the repo instead, for example pip install git+https://github.com/sebaubuntu-python/aospdtgen.

Step 3Get the stock firmware and dump it

Dump the full stock firmware for the exact build on your phone; everything after this step reads from the dump folder.

  1. Find your build so you download the matching firmware:
shell
adb shell getprop ro.product.device        # codename
adb shell getprop ro.build.fingerprint     # exact build
adb shell getprop ro.treble.enabled        # must be true for aospdtgen
adb shell getprop ro.boot.slot_suffix      # non-empty = A/B device
  1. Download the full firmware into ~/android-dt/firmware/. Typical sources:
    • Pixel: Google's factory images or full OTA images
    • Xiaomi/Redmi/POCO: the official fastboot ROM
    • Samsung: the full 4-file firmware (.tar.md5 set) for your exact model and region
    • OnePlus/Oppo/Realme: the full OTA zip containing payload.bin
    • Others: the OEM support site, or a community dump mirror if the OEM does not publish images
  2. Run dumpyara from the venv. By default it writes the dump into a folder named after the firmware file in your current directory; -o picks the location instead:
shell
dtenv
cd ~/android-dt/dumps
python -m dumpyara ~/android-dt/firmware/<firmware-file>.zip -o ~/android-dt/dumps/<codename>

Add -v for verbose logs if anything fails. Expect it to take several minutes and use 3–5× the archive size on disk.

  1. Check the dump. You should see one folder per partition, roughly:
text
<codename>/
  boot/            kernel, ramdisk, dtb from boot.img
  vendor_boot/     on GKI devices: vendor ramdisk, dtb, recovery ramdisk on some
  recovery/        only on devices with a recovery partition
  dtbo/            device tree overlays
  system/          system/build.prop, apps, framework
  system_ext/
  product/
  vendor/          vendor/build.prop, HALs, firmware, init .rc files
  odm/

Confirm system/build.prop and vendor/build.prop exist. If a partition folder is empty, the image format was not recognised; see Troubleshooting.

dumpyara also writes all_files.txt, a sorted list of every file in the dump; grep it to find blobs fast. Before starting it checks for 7z, fsck.erofs and simg2img, and stops with a "You are missing…" error if any is absent (all three come from the Step 1 packages).

  1. Initialise the dump as a local git repo. It makes later blob diffs against a newer firmware trivial:
shell
cd ~/android-dt/dumps/<codename>
git init && git add -A && git commit -qm "Stock dump: <fingerprint>"

Step 4Generate the LineageOS/AOSP device tree with aospdtgen

Point aospdtgen at the dump folder and give it an output path; one command produces the whole device/<vendor>/<codename> skeleton plus the blob list.

  1. Run the generator (always pass -o; without it the tree lands in ./output under whatever directory you happen to be in):
shell
dtenv
python -m aospdtgen ~/android-dt/dumps/<codename> \
  -o ~/android-dt/trees/device_<vendor>_<codename>

Add --no-proprietary-files only if you plan to write the blob list by hand.

The output folder must not exist yet; aospdtgen creates it and stops with an error if it is already there. Delete or rename the old folder before re-running.

  1. Review what it produced. With aospdtgen 1.2.x the tree looks like this:
FilePurposeWhat you usually change
AndroidProducts.mkRegisters the lineage_<codename> product and lunch targetsRarely
lineage_<codename>.mkProduct makefile: inherits AOSP/Lineage common configs and device.mkProduct name, brand, model, fingerprint props; RisingOS flags (Step 8)
device.mkPackages, HALs, overlays, init files and props copied into the buildMost of your HAL and package work happens here
BoardConfig.mkArchitecture, kernel, partition sizes, AVB, recovery, sepolicy dirsPartition sizes, kernel source vs prebuilt, AVB flags
Android.bp / Android.mkSoong namespace and guard so the tree only builds for this deviceRarely
rootdir/bin/ and etc/: init .rc scripts, shell scripts and the generated fstab, copied from stock vendor and recoveryfstab flags, removing OEM-only services
manifest.xmlVINTF HAL manifest from the stock vendor partitionRemove HALs you do not ship
prebuilts/Stock kernel Image, dtb and dtbo when the tree uses a prebuilt kernelReplace with kernel source later if you want
proprietary-files.txtList of blobs to pull from the stock ROM into the vendor treeTrim and annotate (Step 6)
extract-files.py / setup-makefiles.pyLineageOS extract-utils scripts that build vendor/<vendor>/<codename>Nothing; they run from inside a Lineage-based source tree
README.md, LICENSEBoilerplateFill in device specs
  1. Put it under git before touching anything, so every manual fix is a reviewable diff against the generator output:
shell
cd ~/android-dt/trees/device_<vendor>_<codename>
git init && git add -A && git commit -qm "Initial tree from aospdtgen 1.2.x"

The extract-files.py and setup-makefiles.py scripts import LineageOS's tools/extract-utils, so they will not run from ~/android-dt. You run them after the tree is placed inside your synced RisingOS source, which carries the same extract-utils (Step 6).

Step 5Generate a TWRP recovery tree with twrpdtgen

twrpdtgen builds a recovery-only tree from a single image, but its output still uses the retired OmniROM naming, so you must rename three things before it will build on the current TWRP manifest.

  1. Pick the right input image from the dump:
Device layoutImage to feed twrpdtgen
Has a dedicated recovery partitionrecovery.img
A/B with recovery inside boot, no vendor_bootboot.img
GKI device (launched with Android 12+) whose recovery ramdisk sits in vendor_bootNot supported well; start from a published TWRP tree for a device on the same SoC instead

twrpdtgen is confirmed for images from Android 4.4 through Android 12. Newer images may still work, but check every generated value.

  1. Run it. --git commits the result for you; default output is ./output/<manufacturer>/<codename>:
shell
dtenv
python -m twrpdtgen ~/android-dt/firmware/recovery.img \
  -o ~/android-dt/trees/twrp --git

Fastboot ROMs ship the raw recovery.img/boot.img. For OTA-only firmware, re-run dumpyara with -d: debug mode keeps its temp_raw_images/ folder, which holds every partition image unpacked from payload.bin (normally it deletes that folder when it finishes).

  1. Convert the Omni naming to TWRP naming (the twrp-12.1 manifest requires the twrp prefix):
shell
cd ~/android-dt/trees/twrp/<manufacturer>/<codename>
git mv omni_<codename>.mk twrp_<codename>.mk
sed -i 's/omni_/twrp_/g' twrp_<codename>.mk AndroidProducts.mk vendorsetup.sh
sed -i 's#vendor/omni/config/common.mk#vendor/twrp/config/common.mk#' twrp_<codename>.mk
git commit -qam "Rename Omni product to TWRP"
  1. Check BoardConfig.mk by hand before the first build: TARGET_ARCH, BOARD_KERNEL_CMDLINE, BOARD_*_PARTITION_SIZE, TW_THEME (portrait_hdpi for most phones), and BOARD_USES_RECOVERY_AS_BOOT on A/B devices.

The TWRP tree goes in device/<manufacturer>/<codename> inside a TWRP source checkout, not inside your RisingOS source. Keep it in its own git repo, separate from the ROM tree.

Step 6Build the vendor tree from proprietary blobs

The vendor tree is generated, not written: trim proprietary-files.txt, then let LineageOS's extract-utils copy those blobs out of your dump into vendor/<vendor>/<codename>. This step runs inside your synced RisingOS source (set up in Step 8, part 1), because the scripts import tools/extract-utils.

  1. Trim the generated list. aospdtgen is generous; remove anything the ROM already builds from source or that you will never ship:
    • OEM apps, overlays and analytics (priv-app/, app/, OEM framework/ jars) unless a HAL depends on them
    • Duplicates of AOSP HALs that Lineage provides
    • Keep: camera, audio, display, sensors, fingerprint, RIL/IMS, Wi-Fi/Bluetooth firmware, DSP/firmware (vendor/firmware, vendor/lib*/, vendor/etc/)

Useful markers in the list: a leading - builds the blob as a prebuilt module instead of a plain copy, and |<sha1> pins a blob to a known hash so later re-extractions catch silent changes.

  1. Place the device tree in the ROM source and run the extractor against your dump folder:
shell
cd ~/android/rising
mkdir -p device/<vendor>
cp -r ~/android-dt/trees/device_<vendor>_<codename> device/<vendor>/<codename>
cd device/<vendor>/<codename>
./extract-files.py ~/android-dt/dumps/<codename>

With no argument it pulls over adb from a connected, rooted device instead; the dump folder is more reproducible.

  1. Regenerate just the makefiles after editing the list, without re-copying blobs:
shell
./setup-makefiles.py
# or: ./extract-files.py -m ~/android-dt/dumps/<codename>

Other options worth knowing: -k (kang) recomputes the pinned hashes after you swap a blob in on purpose, -s <pattern> re-extracts one section only, and -n skips wiping the vendor tree first.

  1. Commit the vendor tree to its own repo (vendor_<vendor>_<codename>). Blobs are large; enable Git LFS for *.so, *.apk and firmware files, or keep the repo private.

Proprietary blobs are copyrighted by the OEM and SoC vendors. Publishing them is common practice in the custom-ROM community but not licensed; keep that in mind before pushing a vendor tree to a public repo.

Step 7Clean up the generated tree

The generator guesses from the dump; this pass replaces guesses with values read off the real device. Work through it as a checklist and commit after each item so a broken build points at one change.

Read live values from the phone first; they beat anything inferred from images:

shell
adb shell getprop | grep -E 'ro.product|ro.build|ro.boot|dynamic_partitions|ro.vendor.api_level'
adb shell ls -l /dev/block/by-name/            # partition names
adb shell cat /proc/cmdline                    # needs root on most devices
adb shell lpdump                               # super partition groups and sizes (root)

BoardConfig.mk

Kernel

device.mk, rootdir and props

VINTF and SELinux

When every box is ticked, tag the commit (git tag bringup-1) so you can always return to the first known-good state.

Step 8Test-build and flash safely

A tree is only proven by a build that boots. Sync a ROM (or TWRP) source once, drop your trees in, build, and test with temporary boots before you flash anything permanently.

Part 1 — RisingOS Revived source (also needed for Step 6)

RisingOS Revived 9.0 (codename elefthería) is built on LineageOS 24.0 (Android 17, android-17.0.0_r1), so your aospdtgen tree drops in as-is: it keeps the lineage_<codename> product name, the vendor/lineage/config/common_full_phone.mk inherit and Lineage's tools/extract-utils. Only the branch, flags and build commands differ.

  1. Install the ROM build packages (LineageOS's list for current Ubuntu LTS, which RisingOS shares):
shell
sudo apt install -y bc bison build-essential ccache curl flex g++-multilib gcc-multilib \
  git git-lfs gnupg gperf imagemagick protobuf-compiler python3-protobuf \
  lib32readline-dev lib32z1-dev libdw-dev libelf-dev libgnutls28-dev lz4 \
  libsdl1.2-dev libssl-dev libxml2 libxml2-utils lzop pngcrush rsync \
  schedtool squashfs-tools xsltproc zip zlib1g-dev
  1. Install repo, enable ccache, and sync the RisingOS Revived 9.0 branch (seventeen in the manifest README at the time of writing; check the manifest before syncing):
shell
curl https://storage.googleapis.com/git-repo-downloads/repo > ~/bin/repo && chmod a+x ~/bin/repo
echo 'export USE_CCACHE=1 CCACHE_EXEC=/usr/bin/ccache' >> ~/.bashrc && source ~/.bashrc
ccache -M 50G
mkdir -p ~/android/rising && cd ~/android/rising
repo init -u https://github.com/RisingOS-Revived/android -b seventeen --git-lfs
repo sync -c --no-clone-bundle --optimized-fetch --prune --force-sync -j$(nproc --all)

The other branches on that manifest are older releases (fifteen, sixteen, qpr2, sixteen-qpr2); seventeen is the one whose vendor/rising/config/version.mk sets RISING_VERSION := 9.

  1. Add your trees at device/<vendor>/<codename> and vendor/<vendor>/<codename> (Step 6 creates the vendor one). For the long run, list both in .repo/local_manifests/<codename>.xml pointing at your GitHub repos so repo sync keeps them.
  2. Add the RisingOS flags to lineage_<codename>.mk. Keep comments on their own lines: in a makefile, VAR := true # note stores the trailing spaces as part of the value, and ifeq ($(VAR),true) then fails.
makefile
# RisingOS
# Maintainer name in the lunch banner; also checked against the official maintainers list
RISING_MAINTAINER := <your-name>
# ro.rising.chipset / ro.rising.maintainer (skip if init_<codename>.cpp sets them)
PRODUCT_BUILD_PROP_OVERRIDES += \
    RisingChipset="<SoC name>" \
    RisingMaintainer="<your-name>"

# GApps: true ships full GApps (GAPPS build); false for a vanilla build
WITH_GMS := true
# With WITH_GMS := true, ship the smaller core GApps set instead (CORE build)
#TARGET_USES_PICO_GAPPS := true
# With WITH_GMS := false, add microG (MICROG build)
#WITH_MICROG := true

# Under-display fingerprint (adds the UDFPS animations and icons)
TARGET_HAS_UDFPS := true
# Blur, false by default; leave false on weak GPUs
TARGET_ENABLE_BLUR := true
# true drops the bundled Aperture camera
PRODUCT_NO_CAMERA := false

Evolution X flags from an existing tree map like this: WITH_GMS, TARGET_HAS_UDFPS and TARGET_ENABLE_BLUR carry over unchanged; TARGET_USES_MINI_GAPPS becomes TARGET_USES_PICO_GAPPS; TARGET_INCLUDE_BOOT_ANIMATIONS and TARGET_DISABLE_EPPE do nothing here and can go (vendor/rising already sets PRODUCT_ENFORCE_PACKAGES_EXIST := false).

There is no EVO_BUILD_TYPE equivalent. RisingOS sets the build type itself: OFFICIAL only for devices and maintainers listed in vendor/official_devices, UNOFFICIAL for a listed device with an unlisted maintainer, and COMMUNITY for everything else, which is what a new port gets.

  1. Build. riseup is RisingOS's wrapper around lunch lineage_<codename>-<release>-<variant>; it reads the release code from vendor/lineage/vars/aosp_target_release (currently cp2a), so you never type it. rise b runs m installclean and then m bacon on all cores:
shell
. build/envsetup.sh
riseup <codename> userdebug   # = lunch lineage_<codename>-cp2a-userdebug; user for releases
rise b
# quicker iterations (skip rise, which always runs installclean first):
# m bootimage vendorbootimage dtboimage

Other rise modes: rise fb builds a fastboot update package, and gk -s followed by rise b signs with your own release keys instead of the test keys (rise help and gk -h list the rest). Output lands in out/target/product/<codename>/: the flashable RisingOS-9-<date>-<GAPPS|CORE|VANILLA|MICROG>-COMMUNITY-<codename>-ota.zip with its .sha256sum, plus boot.img, vendor_boot.img, dtbo.img.

Part 2 — TWRP source (only for the recovery tree)

shell
mkdir -p ~/android/twrp && cd ~/android/twrp
repo init --depth=1 -u https://github.com/minimal-manifest-twrp/platform_manifest_twrp_aosp.git -b twrp-12.1

Part 3 — Flash and test (the user does this by hand)

  1. Back up first: copy stock boot, vendor_boot, dtbo, vbmeta and recovery images from the firmware into a safe folder, and keep the full stock firmware for a clean restore.
  2. Test without writing when the device allows it: fastboot boot out/target/product/<codename>/recovery.img (or boot.img). Many newer devices refuse fastboot boot; then flash only the inactive A/B slot.
  3. Flash the ROM through the recovery built alongside it (RisingOS builds Lineage-based recovery): flash its boot/vendor_boot/dtbo, reboot to recovery, factory reset, then adb sideload RisingOS-9-*-ota.zip.
  4. Capture logs on every failed boot: adb logcat -b all > logcat.txt, adb shell dmesg > dmesg.txt, and adb shell cat /sys/fs/pstore/console-ramoops* after a reboot loop.

Never flash a test build to a device you cannot restore. Keep the stock firmware and a working fastboot path before every flash.

Troubleshooting

Most failures trace back to a missing host tool, the wrong firmware, or a value the generator guessed wrong. Find the symptom, apply the fix, re-run only the failed step.

Quick reference

The whole pipeline for one device, start to finish, assuming the Step 1–2 setup is done:

shell
# 0. tools
source ~/android-dt/.venv/bin/activate

# 1. dump firmware
python -m dumpyara ~/android-dt/firmware/<firmware>.zip -o ~/android-dt/dumps/<codename>

# 2. ROM device tree
python -m aospdtgen ~/android-dt/dumps/<codename> -o ~/android-dt/trees/device_<vendor>_<codename>

# 3. TWRP tree (optional), then rename omni_ -> twrp_
python -m twrpdtgen ~/android-dt/firmware/recovery.img -o ~/android-dt/trees/twrp --git

# 4. vendor tree (inside RisingOS source)
cd ~/android/rising/device/<vendor>/<codename> && ./extract-files.py ~/android-dt/dumps/<codename>

# 5. build
cd ~/android/rising && . build/envsetup.sh && riseup <codename> userdebug && rise b

Versions checked for this guide: dumpyara 1.0.10, aospdtgen 1.2.1, twrpdtgen 3.0.0 (PyPI), RisingOS Revived manifest branch seventeen (RisingOS 9, LineageOS 24.0, Android 17.0.0_r1, release code cp2a; checked 2026-10-13), TWRP minimal manifest twrp-12.1.
